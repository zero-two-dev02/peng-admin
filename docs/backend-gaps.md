## 本轮源码核实的修正

### 积分 memberUserId 实际是 System 用户 ID

MemberPointController 将 memberUserId 传入 MemberPointService；后者调用 MemberProfileService.get/lock，按 system_user_id 查找，不是按会员档案 id。页面明确显示 System 用户 ID。

- 查询必须填写 ID：ReqVO 虽允许为空，但 Service 使用 primitive long，空值存在拆箱风险。
- 调整会自动激活会员，当前后端没有向 System 校验用户确实存在；操作者必须核实目标，不能随便测试真实用户。
- 建议后端将字段明确命名为 systemUserId 或改为 memberProfileId 并统一语义，同时校验目标存在。
- 当前响应流水没有会员/用户 ID；界面以本次已提交筛选为范围，不虚构响应字段。

### 积分和库存的幂等范围

重复 businessType + businessNo 返回 data=false，不代表本次参数与原请求一致。页面锁定原业务意图并要求查询对应流水，比对变动量与原因，不显示“又成功增加一次”。结果不确定时不自动重试；同意重试也必须复用原业务号。

### 时间语义

- System 操作审计和 Notice 操作审计由数据库 `CURRENT_TIMESTAMP` 写入无 offset 的 `LocalDateTime`；页面按部署数据库墙上时间原样提交和显示，不能擅自加八小时。
- Notice 的计划发布字段由服务的 UTC `Clock` 解释；页面仅对这一明确字段执行本地时间与 UTC 的转换。
- Product、Member、Inventory 的时间也由数据库 `CURRENT_TIMESTAMP` 写入。
- Payment paidAt 与事件/审计时间也由数据库写入，无 offset；页面原样显示/查询数据库墙上时间，不擅自附加 Z。
- 建议后端统一明确时区或返回带 offset 时间。当前 Payment 输入必须按部署数据库时区理解。

### Payment 数量核对不等于资金对账

成功支付数按 paidAt、事件数按 createTime 过滤，两端包含起止边界。差值为成功支付数减回调事件数。没有金额汇总、逐笔匹配或缺失明细。零差值不能证明无遗漏或资金一致；历史成功支付可能早于事件表上线。

### 当前安全/交互边界

- Token 仅内存，刷新后重新登录；无刷新 Token/HttpOnly Cookie 能力。
- 前端权限是 UI 快照；写接口最终由后端验证，权限拒绝后需刷新。
- 用户角色/角色权限为完整替换，后端没有版本参数，无法完全消除两个管理员同时编辑带来的覆盖。页面提供加载保护和增删确认；后端长期应提供关系版本/If-Match。
- 商品没有独立新增 SKU、上传或删除接口；不添加对应入口。
- 支付单响应只有 id/paymentNo/orderNo/amountFen/status，不虚构支付时间或用户资料。
- 后端暂时不可用、缺安全登录凭据均不能记为“真实业务已验证”。
